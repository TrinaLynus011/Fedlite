# FedLite-Care Mechanism Audit

## 1. Technical Problem
The repository implements a sequential federated learning loop for hospital readmission prediction under privacy and communication constraints. The technical problem addressed by the adaptive mechanism is that a static federated configuration can keep a fixed compression ratio, fixed local training effort, and fixed participation rate for all rounds even when the observed utility, privacy cost, and communication load differ from round to round.

The system therefore collects completed-round telemetry and uses it to choose the next round’s configuration. The purpose is not to claim novelty or patentability; it is to document the actual technical mechanism that was implemented.

## 2. System Inputs
The controller consumes telemetry generated by the sequential simulator after each completed round. The implemented inputs include:

- round number
- validation loss
- validation AUROC
- validation AUPRC
- validation F1
- validation precision
- validation recall
- validation specificity
- validation balanced accuracy
- validation Brier score
- validation accuracy
- threshold
- participating client count
- total client samples
- upstream bytes
- downstream bytes
- total bytes
- cumulative communication bytes
- local gradient statistics
  - mean gradient norm
  - median gradient norm
  - fraction clipped
- clipping norm
- noise multiplier
- epsilon value from the privacy accountant
- privacy budget value from controller config
- communication budget value from controller config
- training time per round

These values are assembled in `src/federated/server.py` and passed to `AdaptiveFederatedController.observe()` in `src/federated/adaptive_controller.py`.

## 3. Controller State
The actual controller state is a configuration object loaded from `configs/adaptive_controller.yaml` together with a rolling history list of observed telemetry. The implementation keeps:

- controller enabled flag
- seed
- privacy config
- communication config
- utility config
- resource config
- candidate set
- objective weights
- telemetry history

The controller class is `AdaptiveFederatedController` in `src/federated/adaptive_controller.py`. The state is stored in instance attributes such as `self.config`, `self.history`, `self.candidates`, and `self.objective_weights`.

## 4. Hard Constraints
The implemented filtering logic is in `AdaptiveFederatedController._evaluate_constraints()`.

The controller rejects a candidate when:

- privacy budget is exhausted, if configured and epsilon is known
- communication budget is exhausted, if configured and cumulative communication exceeds the configured threshold
- utility falls below a configured minimum AUROC or AUPRC threshold
- resource time exceeds a configured maximum round time

The logic is intentionally deterministic and uses the latest observed telemetry values from the completed round.

## 5. Candidate Configuration Space
The candidate generation space is defined in `AdaptiveFederatedController._candidate_space()`.

The implementation generates the Cartesian product of:

- compression ratios from `adaptive_controller.candidates.compression_ratios`
- local epochs from `adaptive_controller.candidates.local_epochs`
- participation fractions from `adaptive_controller.candidates.participation_fractions`

For example, the active configuration defines values such as:
- compression ratios: 1.0, 0.5, 0.25, 0.1, 0.01
- local epochs: 1, 2, 3, 5
- participation fractions: 0.6, 0.8, 1.0

The resulting candidate structure is a dictionary with:
- `compression_ratio`
- `local_epochs`
- `participation_fraction`

## 6. Candidate Evaluation
Candidate evaluation is performed in two stages:

1. Hard filtering in `_evaluate_constraints()`
2. Deterministic heuristic scoring in `_score_candidate()`

The score combines:

- utility term based on observed AUROC and candidate local epochs / participation / compression
- communication term based on compression ratio and participation fraction
- resource term based on local epoch count and participation fraction
- privacy term based on the privacy-budget pressure and the candidate’s training intensity

The score is:

- utility score positively weighted
- communication cost negatively weighted
- resource cost negatively weighted
- privacy pressure negatively weighted

The implementation uses the highest valid score and deterministic tie-breaking based on lower compression ratio, lower epoch count, and lower participation fraction to avoid random selection.

## 7. Selected Action
The selected action is implemented in `AdaptiveFederatedController.select_next_configuration()` and returned as a candidate dictionary.

The controller may select:

- `compression_ratio`
- `local_epochs`
- `participation_fraction`

This action is then stored in the round metrics under the keys:

- `selected_compression_ratio`
- `selected_local_epochs`
- `selected_participation_fraction`
- `controller_decision`

The action is applied inside the server loop in `src/federated/server.py` before the next round begins, not during the current in-progress round.

## 8. Closed-Loop Mechanism
The implemented closed loop is:

Telemetry
    ↓
Controller State
    ↓
Constraint Evaluation
    ↓
Candidate Evaluation
    ↓
Action Selection
    ↓
Next-Round Configuration
    ↓
Federated Execution
    ↓
New Telemetry

The actual code path is:

- `src/federated/server.py` builds round metrics after each round
- `controller.observe(round_metrics_dict)` records telemetry
- `controller.select_next_configuration(state=round_metrics_dict)` evaluates candidates
- the returned `next_config` is assigned to `current_adaptive_config`
- the next loop iteration uses that config to set client local epochs, participation fraction, and compression ratio

The evidence is persisted in the metadata `round_history` array under `adaptive_controller` in each experiment metadata file.

## 10. Technical Trade-Off
The implemented adaptive mechanism has clear trade-offs:

- improved AUROC relative to the static baseline
- improved AUPRC relative to the static baseline
- reduced communication cost
- a reported privacy epsilon difference of 4.9974 to 4.1397
- higher wall-clock runtime

The runtime increase is not purely overhead from the controller: the actual code uses different selected `local_epochs` and `participation_fraction` values in the adaptive run, which changes the total amount of local training and client work. The code additionally does a complete controller loop and logging on each round.

## 11. Exact Distinguishing Technical Details
The following details are specific to the implemented FedLite-Care mechanism:

- exact telemetry combination: validation metrics + privacy epsilon + communication counters + training time + gradient statistics
- exact constraint logic: privacy budget exhaustion, communication budget exhaustion, utility threshold, time/resource limit
- exact candidate structure: Cartesian product over compression ratio, local epochs, participation fraction
- exact scoring behaviour: deterministic heuristic score combining utility, communication, resource, and privacy pressure
- exact next-round application mechanism: `current_adaptive_config` is updated in the server loop and applied before the subsequent round to each participating client
- exact privacy interaction: the controller evaluates privacy budget pressure using the reported epsilon value from the accounting routine; it does not independently derive a new DP guarantee on its own

The repository therefore implements a concrete adaptive controller over a sequential federated simulation, not a production distributed system or a clinical deployment layer.
